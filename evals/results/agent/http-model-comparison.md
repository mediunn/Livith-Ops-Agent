# HTTP 조사: 3B와 14B 비교

실행일: 2026-09-28 (Asia/Seoul). 기준 커밋: `496dcd3`.
실행 ID: `4a405e9b25de4f129a55e09ca222e890`.

후속으로 [90초 호출 제한·모델별 2회 반복 평가](http-repeat-evaluation.md)를 실행했다.
아래는 최초 45초 제한 실험의 기록이다.

## 동일 예산 비교 결과

현재 설정에서는 두 모델 모두 세 비교 사례를 해결하지 못했다. 실패 원인은 다르다.
3B는 필요한 직전 구간 대신 현재 구간의 뒤 절반을 조회하고, 비교 전에 증가·감소를 단정했다.
14B는 세 사례 모두 첫 응답이 호출당 45초 제한에 걸려 판단 내용을 평가할 수 없었다.

| 항목 | qwen2.5:3b | huihui_ai/qwen2.5-abliterate:14b-instruct |
|---|---|---|
| 파라미터·양자화 (로컬 메타데이터) | 3.1B, Q4_K_M | 14.8B, Q4_K_M |
| 필요한 직전 구간 실제 조회 | 0/3 | 0/3 (응답 시간 초과) |
| 세 비교 사례의 정상 완료 | 0/3 | 0/3 |
| 가설 의미 검토 | 비교 전 단정, 반박 사례도 증가 주장 | 응답 없음: 평가 불가 |
| LLM 호출 (수정 재시도 포함) | 10회 (재시도 3회) | 3회 (각각 시간 초과) |
| 실제 토큰 사용량 합계 | 입력 26,364 / 출력 3,062 | 응답 미수신으로 알 수 없음 |
| 빈 데이터 사례 | LLM 없이 종료 | LLM 없이 종료 |

빈 데이터는 코드가 처리하므로 모델 성공률 분모에서 제외한다. 시간 초과 시 예약 토큰은
차감되지만 실제 소비량은 수신하지 못하므로 0으로 해석하지 않는다.

| 사례 | 3B: 선택·종료 | 3B 실행 시간 | 14B: 종료·실행 시간 |
|---|---|---:|---|
| checkout 지연 100 → 800ms | 현재 뒤 절반 요청률·지연 후 중복 선택 오류 | 38.199초 | TimeoutError, 45.275초 |
| orders 요청률 8 → 0 req/s | 현재 뒤 절반 요청률 후 중복 선택 오류 | 39.067초 | TimeoutError, 45.316초 |
| checkout 증가 의심, 실제 800 → 800ms | 현재 뒤 절반 지연 후 중복 선택 오류 | 29.844초 | TimeoutError, 45.198초 |

중복 조회는 실행 직전 검증으로 차단됐다. 3B가 잘못 고른 조건은 수정 재시도 후에도 같았다.
반박 사례에서는 직전 구간을 조회하지 않고 현재 지연이 직전보다 높다는 가설을 `supported`로
기록했다. 근거 ID의 존재 검사는 통과했지만 문장의 비교 주장을 뒷받침하지 못했다.
검토자는 Codex이며 원문과 관측을 대조했다. 독립·블라인드 평가는 아니다.

## 통제한 조건

- 기존 개발용 네 사례와 `http_agent_v1` 프롬프트, 도구·후보·스키마·수정 1회 정책 유지.
- 조사별 180초·도구 6회·모델 8회, 모델 호출당 최대 45초.
- temperature 0, num_ctx 16,384, num_predict 1,024, Ollama 0.34.1.
- 두 모델을 순차 실행. 각각 빈 메시지 chat으로 미리 로딩한 뒤 평가 시작.
  로딩 시간은 3B 2.36초, 14B 11.63초이며 조사 예산에서 제외했다.
- 14B 실행 중 `/api/ps`에는 14B만 있었고 context_length는 16,384,
  size와 size_vram은 모두 11,904,273,611바이트였다.
- 모델별 관측값은 같지만 근거 UUID는 실행마다 새로 생성한다. 바이트 단위로 같은 입력은 아니다.
- 모델별 사례당 1회 실행. 프롬프트·실행 코드 9개 파일 해시를 보존했다.

14B는 abliterate 수정 모델이다. 이번 비교는 설치된 두 모델과 현재 실행 설정의 비교이며,
파라미터 수만 바꾼 통제 실험은 아니다. 반복·새 사례 평가 전에는 일반 성능 우열을 결론내리지 않는다.

이전 3B 실행과 종료 상태·조회 횟수는 달랐지만 이번에도 필요한 직전 조회는 0/3이었다.
이전 결과를 대체하거나 성공한 실행만 선택하지 않았다. 규칙 기준선 강화와 새로운 평가 사례는
이번 작업 범위에 포함하지 않았다.

## 별도 첫 응답 진단

동일 예산 비교가 끝난 뒤, 14B 지연 증가 사례의 첫 receipt에 저장된 **동일 메시지·스키마·생성 옵션**을
재사용해 첫 판단만 다시 요청했다. 클라이언트 대기 상한만 180초로 늘린 진단이며 전체 조사 루프를
실행하거나 비교 점수를 수정하지 않았다.

응답은 **25.376초**에 도착했다. `/checkout`, `http_mean_latency`, `previous`를 선택했고,
가설을 `insufficient_evidence`로 남겼다. 기존 후보·근거 ID 검증도 통과했다.
초기 3B의 잘못된 지표·구간 선택 및 비교 전 `supported` 단정과는 다른 첫 판단이었다.
단, 후속 근거 수집이나 가설 기각까지 실행한 결과는 아니다.

서버 응답의 로딩 시간은 약 0.010초, 입력 평가 시간 0.123초, 출력 생성 시간 24.385초였고,
입력 2,020토큰·출력 197토큰이었다. 실제 시간은 원래 45초 제한보다 짧다. 따라서 대기 상한을
늘린 덕분에 성공했다고 말할 수 없다. 입력 캐시나 실행 상태의 영향을 의심할 수 있으나 원인을
분리 측정하지 않았으며, 최초 시간 초과를 모델의 판단 실패로 해석해서도 안 된다.

현재 결론은 **3B의 판단 실패는 재현됐고, 14B의 전체 조사 품질은 아직 판정할 수 없다**는 것이다.
다음 비교에서는 호출 제한을 두 모델에 동일하게 넉넉히 적용하고 로딩·입력 평가·생성 시간을
분리 수집하며 반복해야 한다. 모델·프롬프트를 동시에 바꾸거나 기본 모델을 바로 교체할 근거는 없다.

## 저장된 증거와 재실행

로컬 원본 디렉터리는 `artifacts/evaluations/http-model-comparison/<실행 ID>/`다.

- `metadata.json`: 커밋·모델 digest·프롬프트와 코드 해시·데이터셋·옵션·예산.
- `summary.json`: 모델·사례별 자동 검사 결과와 실행 시간.
- `model-0/`, `model-1/`: 3B·14B의 SQLite·도구 원본·모델 receipt·보고서.
- `warmup-0.json`, `warmup-1.json`: 모델 사전 로딩 응답과 시간.
- `review-criteria.json`: 결과 검토 기준. 기존 자동 점수와 의미 검토는 구분한다.
- `manual-review.json`: 이번 원문 검토와 모델별 평가 가능 범위.
- `long-timeout-first-decision.json`: 별도 재요청의 전체 응답·시간·후보 검증 결과.

기존 평가 CLI를 사용하면 같은 데이터셋·프롬프트·예산으로 다시 실행할 수 있다.
위 실측은 CLI와 같은 `evaluate()` 함수를 사용하고, 모델 로딩을 별도로 먼저 수행했다.

```bash
uv run python -m ops_agent.cli.evaluate_http_agent --planner llm --model qwen2.5:3b
uv run python -m ops_agent.cli.evaluate_http_agent --planner llm \
  --model huihui_ai/qwen2.5-abliterate:14b-instruct
```

자동 검사 실패 시 기존 CLI는 종료 코드 1을 반환하며 실패 결과도 저장한다.
