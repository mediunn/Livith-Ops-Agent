# Agent 전체 조사 루프 검증

[평가 사용법](../../README.md) · [이전 관측 주장 검증](agent-claim-validation.md)

2026-09-27에 `qwen2.5:3b`로 합성 사례 네 개와 실제 Grafana 조사 한 건을 실행했습니다.
최종 기본 프롬프트는 `ops_agent_v6`입니다. 상태 v3·보고서 v3·관측 계산 정책 v1은 유지합니다.

## 변경과 검증 범위

행동 이유를 40~80자 정도로 작성하도록 요청하고, 줄바꿈 없이 문장부호로 끝나는지
검사합니다. 최대 160자 제한은 유지하며 형식 오류는 `rationale_format`으로 한 번 수정합니다.
이는 문장 끝 형식 검사이며 문법·의미의 완결성을 보장하지 않습니다.

전체 루프 평가에서 모델이 선택 항목인 `claim_ids`를 생략하는 문제를 발견했습니다.
생성 스키마에 해당 필드를 필수로 지정하고 검증 관측이 있으면 하나 이상 선택하도록
제한했습니다. 관측이 있는데 선택이 없으면 `missing_claim_selection`으로 수정합니다.
관측이 없는 경우에는 계속 빈 배열을 사용합니다. 의미적 원인 가설 검증은 아닙니다.

외부 호출 없는 pytest 213개와 Ruff·diff 검사가 통과했습니다. 문장 형식 수정과
실패 원문 보존, 양성·음성 관측, 전체 그래프의 평가 수집기 주입, 기대 결과를 모델에서
제외하는지, 조기 종료·관측 누락을 평가기가 검출하는지를 확인했습니다.

## 합성 관측 + 실제 모델

Grafana 수집기만 합성 수집기로 교체했습니다. 기존 파서·실제 로컬 Ollama·운영 planner·
LangGraph·SQLite·호출/시간/토큰 예산·최종 보고서를 실행했습니다. 모델 응답은 mock이 아닙니다.
기대 결과는 모델에게 제공하지 않았습니다. 각 버전에서 사례당 한 번 실행했습니다.

| 사례 | v5 자동 검사 | 최종 v6 자동 검사 | v6 도구 / 모델 호출 | v6 입력 / 출력 토큰 |
|---|---|---|---|---|
| 요청률 0, 로그 없음 | 통과 | 통과 | 4 / 4 | 9,273 / 454 |
| 요청률 증가, info 로그 | 실패: 관측 누락 | 통과 | 3 / 4 | 10,396 / 616 |
| 경고·오류 레벨, 잘린 로그 | 실패: 수정 후에도 가설 검증 실패 | 실패: 직전 구간 비교 누락 | 3 / 4 | 10,546 / 714 |
| warn/error 문자열을 포함한 info 로그 | 통과 | 통과 | 4 / 4 | 9,547 / 506 |

최종 버전은 네 사례 모두 보고서를 생성했지만 자동 기준은 **3/4 통과**입니다.
증가·경고 관측은 최종 보고서에 보존했습니다. 증가·경고 사례는 각각 모델 수정 호출
한 번을 포함합니다. 최종 버전의 수락된 행동 이유는 29~56자로 문장 중간 잘림은
재현되지 않았습니다. 이 소규모 결과는 일반적 정확도나 재현성 보장이 아닙니다.

v5와 v6는 프롬프트뿐 아니라 생성 스키마·선택 검사도 달라 단순 프롬프트 성능 비교가
아닙니다. 평가 사례로 문제를 발견하고 수정했으므로 독립 평가 세트도 아닙니다.

**18:00:19~18:30:19 KST**였습니다.

## 의미적 검토와 남은 문제

Codex 자체 검토이며 독립적인 사람의 평가가 아닙니다. 다음 문제가 남아 최종 합성 네 건과
실제 조사 한 건에 `codex_free_text_quality_review=false`를 기록하고 서버 반영을 확인했습니다.
이 점수는 완결된 문장·관측과 일치하는 범위·구체적인 다음 확인 항목이라는 검토 기준입니다.

- 요청률 0 사례의 최종 설명이 정상 기준 없이 ‘정상’이라고 단정했습니다. 자동 조건은
  통과했으므로 자동 점수를 설명의 정확도 점수로 해석하면 안 됩니다.
- 경고 사례는 요청한 직전 구간 비교를 생략했습니다. 중간 설명은 경고 문자열 조회를
  요청률 비교와 연결했고, 서비스 로그를 외부 API 관련 로그로 단정하는 가설도 나왔습니다.
- 증가 사례의 다음 확인 항목은 ‘새로운 관측 데이터’라는 일반 문구여서 구체성이 부족합니다.
- info 사례의 한계 항목은 실제 관측 한계를 설명하지 않고 비교 결과를 반복했습니다.
- 실제 조사에서도 호출 실패를 관측하지 않았는데 중간 다음 확인 항목이 호출 실패 원인을
  전제했습니다. 최종 다음 확인 항목은 추가 로그 확인을 반복했습니다.

`semantic_review`는 `pending`으로 유지합니다. 프롬프트·문장 끝 형식 검사만으로는
이 문제를 막을 수 없습니다. 비교 등 필수 조사 항목을 구조화해 종료 전에 확인하는 기능과,
자유 문장의 관측 연결·범위·구체성 검토가 아직 필요합니다.
